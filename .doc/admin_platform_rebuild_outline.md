# SoulTest 管理平台重构大纲（最新执行版）

## 1. 这份文档的作用

这不是一份泛泛而谈的重构说明，而是当前管理平台的执行基线，用来回答三件事：

1. 现在已经做到哪一步
2. 当前最大问题还剩什么
3. 下一步应该按什么顺序继续做

当前阶段的原则很明确：**先把信息架构、页面职责和 UI/UX 做稳定，再逐步补业务功能。**

---

## 2. 当前最新状态

截至本轮，管理平台已经完成基础搭建，并进入第一轮页面级重构，重点进展如下。

### 2.1 已完成的基础能力

1. **后台入口已切换到更隐蔽的路径**
   - 正式入口使用 `/private-room`
   - 旧入口 `/admin` 保留兼容跳转语义

2. **后台安全边界已调整为 Cloudflare Access 前置**
   - `/private-room` 入口应由 Cloudflare Access 直接保护
   - 应用内不再把账号、密码、访问密钥作为正式长期方案
   - 当前操作者身份应来自 Access 断言，并用于记录审计日志

3. **后台一级导航已经成型**
   - Dashboard
   - 题集
   - 商品
   - 验证码批次
   - 安全中心

4. **核心页面骨架已经存在**
   - `Dashboard`：只保留概览、待处理事项与工作入口分发
   - `数据分析`：独立承接趋势、排行、发码分布与经营摘要
   - `题集`：可浏览免费题、付费题、接入状态与基础校验摘要
   - `商品`：可查看商品覆盖题集、活跃批次和主要验证方式
   - `验证码批次`：可筛选、搜索、选择批次并编辑基础策略字段
   - `安全中心`：可查看后台入口、当前防护和会话状态

5. **验证码批次管理已经具备首个可操作版本**
   - 支持按状态筛选
   - 支持搜索批次
   - 支持查看批次详情
   - 支持编辑验证方式、scopeMode、allowQuizSlugs、短时授权有效期、备注等字段

6. **公共题库与后台数据的衔接在继续收敛**
   - Landing 页和公共题集列表已经开始改为通过 API 获取数据
   - 免费题、付费题的展示正在从硬编码方式切换到可管理的数据来源

7. **后台通用壳层已经完成第一轮统一**
   - 共享 admin UI 组件已重组
   - 头部、侧边导航、页面容器和基础状态块开始统一风格
   - 后续页面不再继续各自拼装不同结构

8. **Dashboard 已完成第一轮收敛**
   - 运营总览页已从“信息堆叠”改为“总览 + 待处理 + 快捷入口 + 风险批次 + 最近同步”结构
   - 删除了不必要的题集预览 / 商品预览堆叠
   - 首页职责回到分发和优先级判断

9. **题集页已完成第二轮列表工作台重构**
   - 主表字段进一步收敛为“题集 / 业务状态 / 展示与验证 / 操作”
   - 右侧新增对象详情面板，集中展示访问策略、入口路径和接入状态
   - 付费题可直接跳转到对应批次，并带上 `batchId` 进入策略管理上下文

10. **验证码批次页已升级为可执行的批次工作台**
   - 页面结构已收敛为“批次列表 + 新建批次 + 批次工作台”
   - 已补齐创建、冻结、恢复启用、作废动作
   - 批次动作以 D1 回读结果为准，避免前端假成功

11. **商品页已按“绑题 / 发码”模型重新打磨**
   - 商品页明确回到“商品绑定题集，批次负责发码”的职责边界
   - 主列表字段收敛为“商品 / 绑定题集 / 发码状态 / 操作”
   - 从商品页可直接进入批次工作台，也可直接为商品新建批次

12. **安全中心已完成第一轮工作台化重构**
   - 页面结构已收敛为“安全态势 + 已启用控制 + 下一步加固 + 右侧会话详情”
   - 访问面、控制项和加固计划已从散卡片改为结构化信息块
   - 后续应重点展示 Cloudflare Access 保护状态、当前操作者身份与审计摘要

13. **后台状态提示已开始统一收口**
   - 已新增共享的后台提示组件，用于承接错误、警告与成功反馈
   - 登录页、总览页、题集页、商品页、批次页已开始切换到统一提示样式
   - 后续可继续把空态、加载态与保存反馈统一成同一套规则

14. **应用内登录页已降级为过渡实现**
   - 当前代码中仍保留账号、密码、访问密钥登录页
   - 但这不再是目标架构，后续应由 Cloudflare Access 直接保护 `/private-room`
   - 登录页下线后，安全中心应转为展示操作者身份、保护模式与审计记录

### 2.2 当前阶段结论

现在的后台已经不是“完全不能用”的状态，**基础结构和关键业务对象已经出现，且第一轮 UI/UX 收敛已经开始见效**。但它还没有达到可持续运营的程度，主要问题已经从“没有页面”变成了“剩余页面仍未完全统一、对象页还需要继续标准化”。

## 3. 当前仍然存在的核心问题

虽然基础骨架已搭好，但当前管理平台仍有明显问题。

### 3.1 信息架构已经有方向，但页面呈现仍然混乱

- 页面里仍然存在较多卡片堆叠
- 同一层同时出现摘要、状态、说明、入口、操作，认知负担偏高
- 用户进入后可以“看到很多内容”，但不容易快速判断下一步该做什么

### 3.2 Dashboard 已开始收敛，但其他对象页还未完全跟上

Dashboard 本轮已经回到“总览与分发页”的定位，说明重构方向是正确的。当前主要问题不再是首页，而是商品页、批次页和安全页还没有完全吃到同一套页面逻辑。

### 3.3 商品页与安全页已完成第一轮收敛，题集页与全局状态系统仍需继续补齐

题集页本轮已经完成第二轮收敛，商品页与安全页也已追上同等级的工作台水位，说明“主区聚焦判断 + 侧栏承接上下文”的方向已经成立。当前真正还没补齐的重点，转移到了题集页的更深层对象动作，以及 loading / error / empty / success 等全局状态系统的统一收口。

当前缺少的关键特征包括：

- 题集页还缺更深的对象级管理动作
- 商品、题集、批次之间的串联还可继续增强
- 大量数据场景下的排序、批量处理能力还未补齐
- 全局状态组件和反馈系统还没有完全统一

### 3.4 批次页已形成工作台，但深层运营动作还未补齐

验证码批次页本轮已经形成较清晰的“选择对象 → 调整策略 → 保存反馈”节奏，布局混乱问题已经明显改善。当前剩余问题主要变成：

- 还缺批次创建、轮换、冻结、作废等完整操作
- 还缺操作记录和变更历史
- 还缺针对高风险动作的单独确认机制
- 还缺跨商品 / 跨题集的批次对比视角

### 3.5 视觉系统仍缺统一约束

当前后台的 UI 还没有建立稳定的管理端视觉规则，主要体现在：

- 卡片圆角、留白、内容密度不完全一致
- 标题层级与辅助文案密度不够统一
- badge、按钮、筛选器、空状态还未形成严格复用标准
- 页面布局仍可看出“逐页拼装”的痕迹

## 4. 当前应固定下来的产品模型

后续不应再围绕“页面堆组件”做后台，而应固定为下面这套对象模型。

### 4.1 核心对象

1. **题集**
   - 免费题 / 付费题
   - 对外展示与访问入口的基础载体

2. **商品**
   - 面向交易与权益包装
   - 负责把题集组合成可售卖对象

3. **验证码批次**
   - 当前最重要的运营对象
   - 负责控制验证方式、范围、时效、可用码数量

4. **安全会话与入口保护**
   - 负责管理后台访问本身的安全边界
   - 默认方案应为 Cloudflare Access，而非自管后台账号体系

### 4.2 页面关系

应坚持以下路径，不再反复摇摆：

- Dashboard 只做总览与导航分发
- 列表页负责发现对象和快速判断状态
- 详情页 / 工作台负责查看完整信息并完成编辑
- 安全页只处理后台访问安全，不混入业务配置

## 5. 下一阶段的总目标

下一阶段不是继续往页面里堆功能，而是先完成下面这件事：

**把当前后台从“能看能改的半成品”升级成“结构稳定、阅读清晰、操作路径可信的 SaaS 管理平台”。**

这一阶段的重点不是增加多少按钮，而是解决四个问题：

1. 用户进入页面后能不能马上看懂
2. 同一页面是否只有一个主任务
3. 数据展示是否足够清晰、可比较、可筛选
4. 操作路径是否符合“列表 → 详情 → 编辑 → 保存反馈”的管理逻辑

## 6. 下一阶段 UI/UX 重构原则

这一轮重构必须优先统一 UI/UX，不再接受“想到什么就堆一个区块”的页面方式。

### 6.1 页面结构原则

1. **每个页面只保留一个主任务**
2. **先展示状态，再提供操作**
3. **摘要区、筛选区、列表区、详情区明确分层**
4. **避免同屏过多平级卡片抢焦点**
5. **说明文案只用于解释业务，不写成代码注释式提示**

### 6.2 组件与布局原则

1. **优先采用 reui 的管理端模式和组合方式**
   - 统一 page header
   - 统一 toolbar / filters
   - 统一 table / row list
   - 统一 detail panel / drawer / side panel
   - 统一 empty / loading / error state

2. **统一信息密度**
   - KPI 只保留最关键的 3 到 5 个
   - 列表字段只展示一屏内必须判断的信息
   - 次要信息进入二级区域或详情区

3. **统一文案风格**
   - 英文文案使用 sentence case 或 title case
   - 不使用整段全大写英文
   - 不在页面中放“先看这个，再点那个”式教学文案

4. **统一交互反馈**
   - 搜索、筛选、切换状态要有明确反馈
   - 保存后要有可感知的成功/失败状态
   - 风险动作要有单独确认，不与普通保存并列

### 6.3 视觉风格原则

1. 用更稳定的 SaaS 管理端布局代替大面积自由卡片堆叠
2. 控制大圆角和大留白的滥用，保证数据密度和扫描效率
3. 把 badge 颜色语义固定下来
4. 统一按钮层级，只保留一个页面级主按钮
5. 列表页优先保证清晰和效率，不追求花哨感

## 7. 下一步的具体执行计划

下一步优先级已经明确：**继续统一全局状态系统与关键操作反馈，再补齐批次深层运营能力和题集对象动作。**

### 7.1 第一优先级：统一后台页面框架

目标：让所有管理页先拥有一致的壳层与阅读秩序。

交付内容：

1. 统一 page header 结构
   - 标题
   - 一句话描述
   - 页面级主操作
   - 次级状态或 badge

2. 统一列表页工具栏
   - 搜索
   - 状态筛选
   - 类型筛选
   - 结果统计

3. 统一内容容器
   - 主列表容器
   - 侧边详情容器 / 下方详情容器
   - 空状态、错误状态、加载状态

4. 统一页面间距与模块边界
   - 先定标准，再逐页替换

### 7.2 第二优先级：重构 Dashboard

目标：把 Dashboard 收敛成真正的运营指挥台。

保留：

- 核心 KPI
- 待处理事项
- 快捷入口
- 最近风险或最近变更

移除或下沉：

- 过多对象预览卡
- 冗余说明块
- 可直接编辑的复杂内容

验收标准：

- 用户 5 秒内知道整体状态
- 用户 10 秒内知道下一步该进入哪个对象页

### 7.3 第三优先级：继续补强题集对象动作，并稳定商品页扩展位

目标：在商品页已经完成工作台化的基础上，继续补题集页更深入的对象动作，同时为商品页后续详情能力预留稳定扩展位。

优先事项：

- 商品页继续保持“列表 + 详情”结构，不再回退到堆叠卡片模式
- 商品与题集、批次之间的关联关系继续增强
- 题集页补充更深入的对象级入口，而不再把信息重新塞回主表
- 为后续详情页或批量操作留出稳定扩展位

### 7.4 第四优先级：继续完善验证码批次工作台

目标：在现有工作台基础上，继续补齐更完整的运营动作与安全边界。

下一步建议：

- 增加批次创建、轮换、冻结、作废等动作
- 补操作确认、成功回执和风险提示
- 增加变更历史与审计信息
- 支持从题集页、商品页带上下文进入批次页，并持续增强上下文切换体验

### 7.5 第五优先级：统一状态组件和空态系统

目标：让后台不再出现“每页都长得像不同项目”的问题。

需要统一的内容：

- badge 规则
- 空状态模板
- 错误提示模板
- loading skeleton
- 无数据提示
- 保存成功 / 保存失败反馈

补充说明：

- 当前页面结构已基本收敛，下一步重点不再是继续改页面骨架，而是把状态反馈系统统一成一套稳定规范
- 优先改造批次页、题集页、商品页中仍然存在差异的提示条、空状态和保存反馈

## 8. UI/UX 稳定后再继续补的功能

在展示层和操作层稳定之前，不建议继续扩张功能面。等上述内容稳定后，再按以下顺序补功能。

### P1：业务闭环能力

1. 批次创建
2. 新旧码轮换
3. 批次冻结 / 撤销
4. 批量生成验证码
5. 商品详情页
6. 题集详情页

### P2：安全与运维增强

1. Cloudflare Access 正式接管 `/private-room`
2. 下线应用内账号 / 密码 / 访问密钥登录页
3. 操作日志
4. 风险预警提醒
5. 基于 Access 身份的会话展示与审计能力

### P3：经营增强

1. 更完整的数据趋势面板
2. 批次与商品的运营分析
3. 后台动作审计与回溯
4. 更细粒度的权限与角色能力

## 10. 验收标准

如果这一轮 UI/UX 重构做完，至少应满足以下标准：

1. 用户进入任一页面后，**5 秒内知道自己在看什么**
2. 用户进入任一页面后，**10 秒内知道这页的主任务是什么**
3. Dashboard 不再是信息堆场，而是指挥台
4. 题集页与商品页能够支撑后续题库继续增长，不会越加越乱
5. 验证码批次页能够支撑真实运营操作，而不是只做演示编辑
6. 页面之间有统一的视觉规则和交互规则
7. 后续新增功能可以自然挂接到既有结构，不需要反复推翻页面
