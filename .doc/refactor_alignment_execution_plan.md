## 1. 文档目的

本文件用于把 `.doc/technical_architecture_and_technology_stack_detaile.md` 中已经确定的新架构基线，转换成一份可执行、可验收、可回滚的重构计划。

它解决三个问题：

1. 先做什么，后做什么，避免边改边漂移。
2. 管理后台重构与平台底层重构如何对齐，不各走各的。
3. 在重构过程中，如何保证当前已经落地的测试题仍然可用。

## 2. 本轮重构的硬约束

### 2.1 不可破坏的业务约束

1. 已上线或已可运行的测试题链路必须保持可用。
2. 公共用户主链路不能因为后台重构而失效：
   - `/:slug`
   - `/:slug/test`
   - `/:slug/result/:submissionId`
3. 已有题集的静态题面、结果内容、分享内容不能因底层重构被挪成“暂时不可用”。
4. 重构允许替换底层存储边界与后台实现，但不允许中断当前题集使用。

### 2.2 架构约束

1. `/private-room` 的最终保护边界是 **Cloudflare Access**，不是自管后台账号密码体系。
2. **D1 是当前阶段唯一必需的业务真相源**。
3. 浏览器侧只保留 **`sessionStorage`**：
   - 当前标签页短时 access grant
   - 当前标签页答题草稿恢复
4. 当前基线 **不继续扩大对 KV / R2 的依赖**。
5. 静态题面、结果文案、分享素材继续随前端构建发布。

## 3. 顺序化判断（Sequential Thinking）

### Step 1：先冻结目标边界

先确认最终状态，再决定代码删改顺序：

- 后台入口安全：Cloudflare Access
- 平台真相源：D1
- 浏览器短时态：`sessionStorage`
- 管理后台目标：围绕题集、商品、验证码批次、发布与审计工作流组织

### Step 2：识别当前代码与目标的主要偏差

当前仓库与目标架构的主要偏差如下：

1. 代码中仍存在自管后台登录 / 会话实现。
2. `wrangler`、环境类型和部分运行逻辑仍保留 KV / R2 绑定。
3. 题目草稿恢复仍有 `localStorage` 依赖，不符合标签页级会话边界。
4. D1 中仍混有旧后台账号模型与大量演示 / mock 数据。
5. 管理后台大纲已经部分收敛，但尚未完整对齐新的平台边界与执行顺序。

### Step 3：决定“先安全对齐，后平台增强”

重构顺序必须遵循：

1. **先做低风险边界对齐**，不碰当前题集的可用性。
2. **再移除旧的后台安全实现和冗余依赖**。
3. **最后再推进管理平台功能重建**。

### Step 4：把“删除”改成“收口”

对旧实现不采用一次性大清扫，而采用“先停用、再迁移、后删除”的方式：

- 先把新边界立起来
- 再让旧代码退出主路径
- 最后删除旧表、旧接口、旧 seed

这样可以避免对现有测试题造成连带影响。

## 4. D1 mock 数据处理策略

### 4.1 结论

**不建议把 D1 中的 mock 数据一次性全部删除。**

应该拆成两类：

1. **最小可运行基线数据**
   - 本地联调必须依赖的题集
   - 商品、批次、验证码的最小闭环样例
   - 用于验证公共链路与后台列表页的必要记录

2. **可选演示 / 样例数据**
   - 仅用于 Demo、截图、UI 占位、展示复杂场景
   - 不应混入默认启动 seed

### 4.2 必须优先清理的旧数据

以下内容应优先退出默认基线：

1. `admins` 相关表结构与 seed 数据
2. 仅服务于旧后台登录逻辑的数据
3. 与当前正式题集策略无关、但会污染列表和判断的演示数据

### 4.3 推荐落地方式

1. 保留 `db/seeds/local.sql` 作为 **最小可运行 seed**。
2. 新增可选 demo seed，例如：`db/seeds/demo.sql`。
3. 所有“看起来像 mock，但实际是首批正式题集内容”的数据，改按 **bootstrap data** 管理，而不是继续按 mock 心智维护。

## 5. 分阶段执行计划

## Phase A：文档与边界对齐

### 目标

先把“做什么 / 不做什么 / 先后顺序 / 验收口径”写清楚。

### 交付物

1. 本执行计划文档
2. 对齐后的 `.doc/admin_platform_rebuild_outline.md`
3. 明确“当前测试题必须持续可用”的重构守则

### 完成标准

1. 文档之间不再互相冲突。
2. 管理后台重构顺序从 UI 优先，调整为“边界对齐优先 + UI/UX 收敛并行推进”。

---

## Phase B：低风险运行时对齐

### 目标

在不影响题集使用的前提下，先修正最容易带来边界漂移的实现。

### 范围

1. 答题草稿统一迁移到 `sessionStorage`
2. 兼容读取旧 `localStorage` 草稿，避免用户已有草稿直接丢失
3. 清理前端中对旧后台入口语义的误导性依赖

### 完成标准

1. 现有题集答题、返回、恢复草稿仍然可用。
2. 草稿生命周期与架构文档一致。

---

## Phase C：后台安全边界切换

### 目标

让 `/private-room` 真正回归 Cloudflare Access 保护模型。

### 范围

1. 停用自管后台登录接口与会话写入路径
2. 调整后台 API 鉴权方式，改由 Access 身份透传 / 校验承接
3. 删除旧后台登录页面或会话恢复逻辑中的主路径依赖

### 风险控制

1. 在 Access 方案完全接管前，不直接删除所有旧代码。
2. 先让新鉴权成为默认主链路，再做删除。

---

## Phase D：D1 与 seed 收口

### 目标

把数据库恢复到“可运行、可理解、可维护”的最小状态。

### 范围

1. 清理 `admins` 表与相关查询依赖
2. 拆分默认 seed 与 demo seed
3. 去掉会误导平台状态判断的过量 mock 数据

### 完成标准

1. 本地初始化后仍可完整走通至少一条免费题和一条付费题链路。
2. 后台列表页能基于最小 seed 正常展示。

---

## Phase E：管理平台对象化重建

### 目标

把后台从“页面拼接式管理台”推进为“题集 / 商品 / 批次 / 发布 / 审计”工作台。

### 范围

1. 题集管理：版本、发布、回滚、运行时配置
2. 商品管理：商品与题集解绑 / 绑定关系、权益包装
3. 验证码批次：创建、冻结、撤销、批量生成、规则展示
4. 安全中心：Access 状态、操作者身份、审计摘要

### 原则

1. 不为了“看起来更完整”而先加大屏式 Dashboard。
2. 先补对象动作闭环，再补经营增强能力。

## 7. 验收标准

### 7.1 公共用户链路

1. 题集详情页可正常进入
2. 测试页可正常答题
3. 刷新 / 返回后草稿恢复符合预期
4. 结果页仍可读取已有提交结果

### 7.2 后台链路

1. `/private-room` 的安全边界与文档一致
2. 后台页面结构和对象模型一致
3. 不再让旧后台账号体系成为默认路径

### 7.3 数据链路

1. D1 初始化后即可支撑最小业务闭环
2. 默认 seed 不再夹杂大量展示型 mock 数据
3. 演示数据与正式基线数据清晰分离

---

## 8. 当前执行顺序

本轮按以下顺序落地：

1. 创建本计划文档
2. 对齐 `.doc/admin_platform_rebuild_outline.md`
3. 先落一项低风险运行时对齐：题目草稿切换为 `sessionStorage`
4. 验证当前测试题主链路不受影响
5. 再进入后台安全边界切换

这也是后续继续推进时的默认顺序，除非文档再次调整。
