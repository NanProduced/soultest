# SoulTest 测试题 UI 自定义改造清单与实施规范

## 1. 文档目的

本文件用于回答三个问题：

1. 当前每套测试题分别处于什么页面实现状态。
2. 按"通用详情页 → 通用测试页 → 模板结果页 → 已自定义页精修"的顺序，应该如何排改造队列。
3. 在把全部测试题逐步改造成"一题一套 UI"时，如何避免页面数量上涨后造成包体膨胀、首屏变慢、交互卡顿和维护失控。

本文档作为 UI 改造正式规范使用，后续所有题目的前台改造都应以本文件为基线执行。

---

## 2. 已确认的现状结论

### 2.1 路由与页面机制现状

当前前台页面存在两条实现路径：

1. **免费题独立路由页**
   - 在 `src/app/router.tsx` 中直接挂独立页面组件。
   - 例如：`free/aura`、`free/banwei`、`free/painting`、`free/talent`、`free/szondi`、`free/soul-city`。
   - 这类题的详情页 / 测试页 / 结果页都已经是独立页面。

2. **付费题通用动态路由页**
   - 详情页统一走 `src/pages/quiz-detail-page.tsx`。
   - 测试页统一走 `src/pages/quiz-test-page.tsx`，只有当 runtime 指定 `renderer=custom` 时才切到独立测试页。
   - 结果页统一走 `src/pages/quiz-result-page.tsx`，只有当 runtime 指定 `renderer=custom` 时才切到独立结果页；否则走结果模板注册表 `src/features/quizzes/result-template-registry.ts`。

### 2.2 当前最核心的问题

1. **付费题详情页全部共用一套通用详情页**，这是当前产品感最弱的部分。
2. **多数付费题测试页仍为通用测试页**，题目气质没有被充分表达。
3. **多数付费题结果页仍是模板结果页**，虽然不是同一套模板，但仍然不是"一题一页"的完整表达。
4. **免费题虽然已是独立页面，但视觉质量和组件体系仍未统一**，后续仍需要进入"精修阶段"。
5. **`bigfive` 存在配置与模板注册不一致问题**：runtime 配置为 `bigfive-profile`，但当前结果模板注册表没有该模板键，实际会回退到默认模板。

## 4. 建议改造顺序

按"先解决有无，再解决好坏"的原则，分四阶段推进：

| 阶段 | 目标 | 执行对象 | 原因 |
|------|------|----------|------|
| **Phase 1** | 付费题全部升级为独立详情页 | 10 套通用详情页付费题 | 详情页是第一触点，影响购买转化 |
| **Phase 2** | 通用测试页改为题目专属测试页 | 7 套通用测试页付费题 | 测试过程决定沉浸感和完答率 |
| **Phase 3** | 模板结果页升级为题目专属结果页 | 7 套模板结果页付费题 | 结果页是分享与复访核心 |
| **Phase 4** | 已自定义页面统一精修 | 9 套已独立页面题 | 统一规范、清理差异、提升质量 |

**立即行动项**：
1. 修复 `bigfive` 结果模板注册缺口
2. 建立"自定义详情页注册机制"
3. 选 1-2 套高优先级付费题做详情页试点

## 5. UI 自定义改造正式规范

### 5.1 最终目标

1. **每套题都有自己的详情页、测试页、结果页。**
2. **验证码输入、授权校验、加载态、异常态、分享与导出等基础能力继续共用。**
3. **所有题的视觉表达可以不同，但底层交互壳和性能边界必须统一。**

### 5.2 明确保留统一的部分

以下能力必须统一，不允许每题各写一套：

1. 验证码输入组件
2. 验证码校验请求逻辑
3. access session 写入与读取
4. 答题草稿恢复机制
5. 提交结果请求逻辑
6. 通用错误提示机制
7. 分享导出基础能力
8. 埋点与行为日志接口

也就是说：

- **页面视觉自定义**
- **业务链路统一复用**

### 5.3 明确允许自定义的部分

以下能力允许按题完全自定义：

1. Hero 区布局
2. 详情页叙事结构
3. 测试页进度呈现方式
4. 题目切换动效
5. 结果页核心图表
6. 结果页内容组织方式
7. 页面主视觉、字体层级、背景风格、氛围元素

### 5.4 页面实现约束

每套题的三个页面都应遵守以下约束：

1. **按路由独立拆包**
   - 详情页、测试页、结果页应支持按题懒加载。
   - 不允许把全部测试题页面通过静态 import 一次性打进主包。

2. **不把视觉内容重新塞回 D1**
   - D1 负责业务真相：发布、商品、批次、验证码、授权、提交、分析。
   - 页面视觉、排版、静态文案、结果图素材仍跟随前端代码管理。

3. **禁止继续扩大"一套万能模板"**
   - 可以保留通用壳与基础组件。
   - 不再继续把新题塞进通用详情页 / 通用测试页 / 模板结果页作为长期方案。

4. **允许共享积木，不允许共享审美结论**
   - 共享积木：按钮、卡片、数值块、图表块、FAQ、CTA、Poster 容器。
   - 审美结论必须由具体题目决定，不允许用同一套视觉样板硬套全部题。

## 6. 性能与稳定性红线

为了避免"页面越做越炸"，所有 UI 自定义都必须遵守以下红线。

### 6.1 包体红线

1. 任何新题页面不得通过中心文件静态导入全部页面组件。
2. 任何重图表、导出、动画模块都必须按需加载。
3. 禁止把所有题目的海报底图、结果插图、背景纹理打进首页或目录页包体。

### 6.2 渲染红线

1. 动效优先使用 `transform` 和 `opacity`。
2. 禁止大面积持续模糊、复杂粒子、长时运行背景动画。
3. 大型图表只在结果页视口内加载，不在详情页预渲染完整结果组件。

### 6.3 资源红线

1. 每题资源按题目单独归档。
2. 列表页、目录页、首页只允许加载缩略资源。
3. 长图导出底图与浏览态图像分离管理。
4. 优先使用压缩后的静态图片格式，不引入超大 PNG 作为常规首屏资源。

### 6.4 状态红线

1. 草稿继续保留在 `sessionStorage`。
2. 不允许把整站题目数据一次性持久化进浏览器。
3. 不允许为了视觉自定义而重写授权与提交主链路。

### 6.5 维护红线

1. 每套题必须遵守同一套文件组织规范。
2. 每套题改造时必须补齐"页面风格关键词 + 资源清单 + 性能清单"。
3. 每套题不得复制整套基础逻辑，只能复用共享交互壳。

## 7. 文件组织规范

建议后续按题建立页面入口与资源目录，避免页面数量上来后结构失控。

建议组织方式：

1. `src/features/quizzes/pages/<slug>/intro.tsx`
2. `src/features/quizzes/pages/<slug>/test.tsx`
3. `src/features/quizzes/pages/<slug>/result.tsx`
4. `src/features/quizzes/pages/<slug>/assets/*`
5. `src/features/quizzes/pages/<slug>/config.ts`

共享能力建议继续放在：

1. `src/components/quiz/*`
2. `src/features/quizzes/session.ts`
3. `src/features/quizzes/api.ts`
4. `src/features/quizzes/engine.ts`

## 9. 小红书引流推广规范

UI 优化时需同步考虑小红书店铺引流，但需遵循"自然融入、不破坏美感"原则。

### 9.1 推广素材

| 素材 | 文件路径 | 用途 |
|------|----------|------|
| 小红书店铺名片 | `/images/soultest-card.png` | 品牌展示、店铺入口 |
| 小红书二维码 | `/images/soultest-qrcode.jpg` | 扫码关注引流 |

### 9.2 展示位置建议

以下位置适合自然融入推广元素：

1. **结果页底部**
   - 在"分享结果"区域旁添加"关注小红书获取更多测试"
   - 使用名片形式展示，与结果卡片风格统一

2. **详情页 Footer**
   - 在页面底部关于/帮助区域添加
   - 作为"关注我们"的一部分，不突兀

3. **测试完成后的推荐区**
   - 在"更多测试"推荐下方
   - 以"关注小红书，第一时间体验新测试"引导

### 9.3 设计原则

- ✅ **融入页面风格**：使用与当前题目一致的配色、圆角、阴影
- ✅ **非强制性**：不弹窗、不强制展示、不影响主流程
- ✅ **可关闭/可跳过**：给用户选择权
- ✅ **价值导向**：强调"获取更多测试"而非单纯引流

- ❌ **禁止行为**：
  - 首屏直接展示二维码
  - 测试过程中打断展示
  - 与页面风格严重冲突的设计
  - 过大尺寸占用核心内容区域

### 9.4 图片资源管理

**注意**：以下文件内容重复，统一使用 `soultest-card.png` 和 `soultest-qrcode.jpg`：

### 10.2 架构改造说明

为了承接一题一页，已完成以下架构调整：
1. **统一注册中心**：`src/features/quizzes/pages/registry.ts` 成为 UI 配置的唯一入口，支持全 Lazy 加载。
2. **智能外壳策略**：通用页面容器不再通过硬编码判断 slug，而是通过注册表动态拦截。
3. **视觉标准组件**：沉淀了 `QuizUnifiedPortal`（统一验证/推广入口）、`QuizFeatureGrid`、`QuizOutcomeList` 等高阶积木。
4. **性能红线监控**：已实现 `performance-guard.ts` 实时审计自定义页面的资源与渲染性能。

### 10.3 精修轮视觉准则 (Refinement Standards)

在详情页重构中，确立了以下视觉准则：
- **叙事优先**：首屏聚焦情绪共鸣，移除生硬的功能卡片，采用电影感/叙事化排版。
- **一屏触达**：优化移动端适配，确保标题、简介与激活门户（Portal）在主流屏幕上一屏可见。
- **风格去同质化**：根据测试主题定制视觉背景（如九型人格的深空、大五人格的瑞士极简、压力负荷的生命脉冲）。
- **引流一体化**：使用大尺寸二维码配合 `xhslink` 直达链接，整合进激活链路，提升转化率。

## 10. 结论

当前项目不是"题目数量太多，不适合一题一页"，而是：

1. **页面组织方式还没准备好承接一题一页。**
2. **付费题目前主要卡在通用详情页、通用测试页、模板结果页这三层。**
3. **免费题和少量付费题已经证明独立页面路线可行。**

因此，本项目后续 UI 改造的正式方向确认为：

**验证码组件统一，详情页 / 测试页 / 结果页按题自定义，按路由拆包，按统一性能红线实施。**
